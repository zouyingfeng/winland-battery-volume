# 2.4G 无线键鼠电量 — 可行性报告（实测，2026-10-18）

**结论先行：本机目前读不到任何 2.4G 键鼠电量。** 通用 HID `Battery Strength` 路径全负；
唯一有希望的罗技 HID++ 2.0 路径被一个环境因素卡住（HID++ 2.0 长报文通道在 Logi Options+ 运行时
对独立客户端完全不应答）。代码已按协议实现并交付，但**在把 Options+ 退掉并复测成功之前，
插件不应向用户承诺 2.4G 电量功能**。

测试机：Windows 11 build 26300，Administrator 会话，用户正在使用键鼠；
Logi Options+ 正在运行（`logioptionsplus_updater/agent/logivoice/appbroker.exe`，可能是 HID++ 2.0 通道的占用者）。
实测时间：2026-10-18 09:42–09:49（Asia/Shanghai）。

## 1. 可行性矩阵（逐接收器，均为本机实测）

| 接收器（PnP） | 结论 | 证据 |
|---|---|---|
| **Logitech USB Receiver `USB\VID_046D&PID_C548`（Logi Bolt）** | ⚠️ **理论可读，本机实测被阻塞** | 两个 vendor HID 集合都枚举并打开成功：<br>• `MI_02&COL01`：7 字节 in/out（usage 0xFF00/0x01）= **HID++ 1.0 短报文通道**，在线——发 1.0 读寄存器 `10 FF 83 02 00 00 00` 收到 `10 FF 8F 83 02 02 00`（0x8F 错误帧，0x02=无效地址，说明通道活着）<br>• `MI_02&COL02`：20 字节 in/out（usage 0xFF00/0x02）= **HID++ 2.0 长报文通道**。WriteFile 接受 20 字节 `[11 FF 00 1B …]`（report 0x12 被拒 err=87，证明 0x11 是正确的长报文 ID）；`HidD_SetOutputReport` 同样成功。**但对 `ROOT.getProtocolVersion`、`ROOT.getFeature(0x0001/0x1004/0x1001)`（dev=0xFF 及配对设备索引 1/2/3）在 400–500ms 内均无任何 input report**，两种写 API（WriteFile / HidD_SetOutputReport）结果一致 |
| **Sonix "2.4G Dongle" `USB\VID_0C45&PID_FEFE`** | ❌ 不可读 | 键盘/鼠标/vendor 集合（0xFF60/0xFFFF/0xFF00 等）都没有 HID Battery Strength；未见可控的厂商电池协议 |
| **Rapoo "Rapoo Gaming Device" `USB\VID_24AE&PID_1416`** | ❌ 不可读（本次未深挖） | 9 个 vendor 集合（usage 0xFF00/0x02..0x12、0xFF60），均无 HID Battery Strength；厂商协议未逆向 |
| **"F108Pro Dongle" `USB\VID_05AC&PID_024F`（仿 Apple VID）** | ❌ 不可读 | vendor 集合 0xFFFF/0xFF60/0xFF59，无 HID Battery Strength；厂商协议未知 |
| `IDLE` `USB\VID_2DC8&PID_3109`、`LED Shebei` `USB\VID_0416&PID_A125` | ❌ / 非候选 | 均无 HID Battery Strength；而且不是键鼠候选（后者是 LED 设备） |
| **通用标准 HID Battery Strength（所有品牌）** | ❌ 本机全负 | 48 个 HID 顶层集合逐个读取 report descriptor 派生的 value caps：**0 个**设备暴露 Usage Page 0x06 / Usage 0x20（Battery Strength）|

### Logitech 阻塞点的两种解释（无法在「不打扰用户」约束下区分）
1. **Options+ 抢占了 HID++ 2.0 通道的 input report**：Windows 上多个进程可同时打开 HID 集合，
   但响应报文可能只投递给一个读队列；Options+ 常驻读 0x11 报文，我们的请求有去无回。
2. **Bolt 接收器的 HID++ 2.0 长通道需要 Options+/驱动建立的会话**（或长通道只用于设备通知），
   裸 HID++ 请求被静默丢弃。
两种情况下，**关闭 Logi Options+ 后重新运行 `test-harness` 10 秒即可判定**（见 §5）。

## 2. 协议事实（已核对 Solaar 源码，供后续接手者直接使用）

参考源码已下载到 `refs/`（`solaar_base.py`、`solaar_hidpp20.py`、`solaar_receiver.py`、`solaar_base_usb.py`、
`mingw_hid*.h`、`wine_hidusage.h`）。

- **HID++ 2.0 报文**（report 0x11，20 字节）：
  `[0x11, deviceIndex, featureIndex, (functionId<<4)|softwareId, params(16B, 小端参数)]`
  - `softwareId` 用 `0x0B`（Solaar 固定值；高位置 1 以区分通知）
  - 应答 = 同一 HID 集合的 input report，`[0x11, dev, featureIdx, fnid, params…]`；
    错误帧 `[0x11, dev, 0xFF, featureIdx, fnid, errorCode]`
  - **短报文 report 0x10（7 字节）只属于 HID++ 1.0**；在 Bolt 上把 2.0 请求发到 7 字节集合会得到
    `10 FF 8F 00 1B 01 00`（0x8F 错误帧，0x01=InvalidSubID）
- **C548 的两个 vendor 集合是分开的**（Windows 上表现为两个 HID 顶层集合/设备接口）：
  7 字节集合 = 1.0；20 字节集合 = 2.0。写 20 字节必须写到 20 字节集合的句柄。
- **设备枚举**：接收器自身 deviceIndex = `0xFF`；配对设备索引 `1..6`（Bolt 最多 6 台）。
  逐索引发 `ROOT(0x0000) function 1 = getProtocolVersion` 探测在线；空槽位接收器会很快回错误帧。
- **电池特性**（Solaar `hidpp20.py` 的 `battery_functions`）：
  - `UNIFIED_BATTERY 0x1004`：function **1**（Solaar 传 `0x10`）：`[dischargeLevel, level, status, ignore]`，
    `level`: 8=full/4=good/2=low/1=critical/0=empty；百分比取 `dischargeLevel`（0=未知）
  - `BATTERY_STATUS 0x1000`：function 0：`[level, nextLevel, status]`（大端，level 0=未知）
  - `BATTERY_VOLTAGE 0x1001`：function 0：`[voltageHi, voltageLo, flags]`，mV；百分比需按曲线估算
    （Solaar 曲线已抄进代码，界面必须标注「估算」）
  - `DEVICE_NAME 0x0005`：function 0 = 名称长度，function 1 = 按 offset 取 UTF-8 分片
- **通用 HID Battery Strength**：Usage Page `0x06`（Generic Device Controls）/ Usage `0x20`
  （Battery Strength，HID Usage Tables 1.12 §9.2）。用 `HidP_GetValueCaps` 检测（不需要解析裸 descriptor），
  Feature report 用 `HidD_GetFeature` + `HidP_GetUsageValue` 读取。
- 枚举 HID 集合：**CfgMgr32**（`CM_Get_Device_Interface_List_SizeW/ListW` + GUID_DEVINTERFACE_HID
  = `{4D1E55B2-F16F-11CF-88CB-001111000030}`）比 SetupAPI 简单可靠（本机 SetupAPI
  `SetupDiEnumDeviceInterfaces` 返回 0 个设备，原因未深究；CfgMgr32 一次成功）。

## 3. 交付代码

### `HidBatteryReader.cs`（可直接拷进插件 `Devices/`，纯 P/Invoke，无 NuGet/WinRT）

```csharp
internal static class HidBatteryReader
{
    // 返回所有读到的 2.4G 设备；读不到就返回空列表，永不抛异常
    internal static List<HidBatteryDevice> Read();               // 默认 280ms 总预算
    internal static List<HidBatteryDevice> Read(int budgetMs);   // 调试用

    internal static IReadOnlyList<string> LastTrace { get; }     // 诊断日志（插件可忽略）
}

internal sealed class HidBatteryDevice
{
    public required string Id;        // "hid:logitech:c548:1"
    public required string Name;      // HID++ DEVICE_NAME，失败时 "Logitech wireless device N"
    public string Transport;          // "2.4G"
    public int? Percent;              // 0..100；null = 特性在但没读到值（绝不编造）
    public string? Detail;            // 协议/特性 ID/电压等证据
    public bool Connected;
}
```

实现要点：

- 路径 B：CfgMgr32 枚举 HID 集合 → 只挑 046D 接收器 PID、vendor 集合、**outLen>=20** 的 HID++ 2.0 接口 →
  `ROOT.getProtocolVersion` 确认接收器 → 索引 1..6 探测 → `DEVICE_NAME` + 电池特性（0x1004 → 0x1000 → 0x1001）。
  特性索引/设备名跨调用缓存（静态字典），热路径只发必要请求。
- 路径 A：全量 HID 集合扫 Battery Strength（`HidP_GetValueCaps`），Feature report 读取；Input-only 时尝试被动读一次。
- 全程 `Stopwatch` 截止时间：每个请求 `min(单次超时, 剩余预算)`，超时/异常/错误帧一律跳过；
  句柄 `GENERIC_READ|WRITE`、`FILE_SHARE_READ|WRITE`、`FILE_FLAG_OVERLAPPED`，用完立刻关闭。
  只发只读 HID++ 查询（getProtocolVersion/getFeature/读电池特性/DEVICE_NAME），**不写任何设备配置**。
- 本机实测耗时：冷启动 172ms；热读 3 次 277/155/156ms（首轮含一次 HID++ 2.0 超时等待，之后走缓存），
  即使全部读不到也 <300ms（默认 280ms 预算内，永不抛出）。

### 集成建议

插件现有模型是 `BatteryDevice { Id, Name, Percent?, Connected, Transport, Detail? }`
（`bluetooth-battery/Devices/BatteryDevice.cs`，Transport 已预留 `"2.4G"`）。
两种接法：
1. 把 `HidBatteryDevice` 改成直接返回 `BatteryDevice`（`Transport = "2.4G"`，`Category` 按名字猜 Mouse/Keyboard）；
2. 或保留本类型，在数据层里做一次映射。
在检测到 `Logitech wireless device N` 时，由于接收器不提供设备类型，建议名称增加后缀
（`罗技无线设备 1（接收器配对）`），并允许用户手动重命名/隐藏。

## 4. 明确不行的（负证据）

- 本机 48 个 HID 顶层集合中，**没有任何设备实现标准 HID Battery Strength**（Usage 0x06/0x20）。
  所以「通用 HID 电量」对 Sonix/Rapoo/F108Pro 这些国产 2.4G 接收器完全无效。
- 罗技接收器的 7 字节短接口在 HID++ 2.0 下不可用（只回 1.0 错误帧）。
- 把 HID++ 2.0 请求发到短接口 / 用短报文：接收器回 `10 FF 8F 00 1B 01 00`（InvalidSubID）。
- HID 电量 PnP 属性不存在（Lead 已证明；本次也验证了报描述符层面同样没有）。
- 本机 `USB\VID_2D99&PID_E032`（HECATE G4 S PRO 耳机）等非键鼠设备也顺带扫过，无 Battery Strength。

## 5. 后续验证步骤（需要用户同意，10 分钟）

1. 让用户从托盘 **退出 Logi Options+**（Options+ → 退出，不是关窗口）。
2. 运行：`_research/hid-proto/test-harness> dotnet run -c Release`（或只跑 `ProbeLogitechVariants`）。
3. 若 [D2] 出现 `LONG root... REPLY 11 FF 00 1B ...`，则 HID++ 2.0 可用，`HidBatteryReader.Read()`
   应立刻返回真实百分比（接收器单设备通常 <100ms）；此时把 reader 并入插件即可。
4. 若仍 NO_REPLY，则需要抓 Options+ 的 HID 报文（USBPcap/Wireshark，需装驱动，超出本次范围）
   或改走 Options+ 的私有本地接口（无文档，不建议）。
5. 若坚持支持非罗技品牌：只能逆向 Sonix/Rapoo 厂商 HID 报文（产出慢、风险高，不建议为 2.4G 电量投入）。

## 6. 风险与安全

- 只读请求、共享句柄、无独占锁：不会影响用户正在使用的键鼠（本次测试期间键鼠正常）。
- 不会修改配对/DPI/宏/灯光；不重启 WinIsland；不改插件目录。
- 读不到时插件应静默省略 2.4G 设备（或显示「—」），不要显示假电量。
- 罗技 HID++ 电池字段若将来读到：`UNIFIED_BATTERY`/`BATTERY_STATUS` 的 `dischargeLevel` 可直接用；
  `BATTERY_VOLTAGE` 只能标「估算」。
